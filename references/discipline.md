# 工作纪律

移植周期长、失败多、经常换人或换 agent 接手。能否持续推进，主要取决于记录是否及时准确，而不是某次调试多聪明。下面写的是**必须做到的事和必须记录的内容**；文档的具体格式由你自己决定，清楚、好找、能被下一个人直接接手即可。

## 1. 必须有的文档，以及要记什么

| 文档 | 要记什么 |
|---|---|
| `AGENTS.md`（或项目的 agent 规则文件） | 设备和目标；用户已确认的决策（带日期）；授权边界（哪些操作可以无人值守）；设备安全规则；提交署名规则；什么不能进公开仓。不写当前进度。 |
| 状态表 | 每个功能一句话状态（只用状态词）和详细文档链接；**唯一的下一步**；当前阻塞；设备现在是什么状态、谁在操作、有没有正在运行的任务。 |
| 工作日志 | 按日期记**结论的变化**，不记流水账。 |
| 每个功能一份详细文档 | 路线和复用来源；证据（每条带版本信息）；排查过程和最早出错的层；被否定的假设（保留原文，追加适用范围）；完成标准；下一个实验。 |
| **技术债表（唯一一份）** | 见下一节。 |
| 放弃方案记录 | 放弃了什么、证据、在什么条件下成立、重新考虑需要什么新证据。 |
| 实验记录 | 改了什么、预期结果各说明什么、判据、结果（机器证据和人工确认分开）、证据位置。 |
| 对外文档 | 写给第一次接触项目的人：风险、安装、升级、回到 Android、支持表。不写内部代号和进度细节。 |

状态只用这几个词：待调研、有源码线索、离线通过、真机启动、真机通过、真机失败。

## 2. 技术债：快速方案必须登记

为了尽快点亮或跑通，可以先用临时做法（例如借用固件画面、固定发射功率、保守增益、调试参数、全局忽略开关、应用级绕过、手工步骤）。这完全可以，但**每一个临时做法都要登记在一份统一的技术债表里**，之后集中还。

每条至少写清：
- 做了什么临时处理，放在哪里（文件、包、配置项）。
- 为什么暂时需要它，正确的做法是什么。
- 它带来的影响和风险（功能、功耗、安全、维护）。
- 去掉它的条件（什么完成之后、怎么验证可以去掉）。
- 关联的功能文档。

规则：
- 加临时做法和登记技术债在同一个提交里完成。
- 功能"跑通"不等于债还清；链路通了之后仍要回来收敛。
- 普通的"还没做的功能"不放技术债表，放状态表。
- 定期按影响排序过一遍，挑出下一批要还的。

## 3. 什么时候写

- 开始一个功能前：写目标、路线、完成标准。
- 每次上机前：写实验的预期和判据；上机后当天写结果和证据位置。
- 结论变化：更新工作日志和状态表。
- 加临时做法：登记技术债。
- 放弃方案：写放弃记录。
- 用户做了决定：写进 AGENTS.md。
- 同样的失败第二次出现：写一段分析，包括最早出错的层、已排除的假设、下一个能证伪的实验。
- **会话结束或交接前**：更新状态表的下一步、阻塞和设备状态。下一个接手的人或 agent 只看文档就能继续。
- 子 agent 完成任务时，也要按同样的要求更新它负责的记录；主 agent 检查。

写法：
- 写结论和证据，不写流水账；原始日志放 `private/`，文档里只放路径。
- 一个结论只写在一个地方，其他地方链接过去。
- 失败和回退追加新记录，不改旧记录。
- 每条真机结论带：源码提交、镜像哈希、测试场景、证据位置。
- 新规则写进 AGENTS.md 时，尽量同时加一个自动检查，否则很快会被忘掉。

## 4. 目录结构

推荐一个私有工作区，里面嵌套两个独立的公开仓库（工作区的 `.gitignore` 忽略它们）：

```
<项目>-workspace/                 私有工作区，仅本地 Git
├── AGENTS.md
├── docs/                         状态表、工作日志、技术债、放弃方案、功能文档、调研与实验记录
├── tools/                        内部脚本：上机编排、采集、分析
├── sources/                      参考仓库（只读，记录来源和提交）
├── private/                      Git 忽略：原始日志、备份、本机唯一数据
├── out/                          Git 忽略：构建输出和缓存
├── kernel/                       内核仓（独立 Git，公开，保留上游历史）
└── public/<项目>/                集成仓（独立 Git，公开）
    ├── README.md                 风险、快速开始、"让 AI 帮你安装"提示词、支持表
    ├── docs/                     安装、升级、构建、开发文档
    ├── kernel/                   内核提交和配置的锁定信息、ABI 账本
    ├── device/                   设备用户态
    ├── packaging/                各个软件包
    ├── firmware/                 原厂固件（用户同意分发时）
    ├── tools/                    构建、打包、安装、切换、测试
    └── tests/                    测试，测试数据来自真机
```

- 同一份代码只放一个地方：内核改动在内核仓，集成代码在集成仓，私有工作区只放记录和内部脚本。不保存长期同步的副本。
- 序列号、MAC、蓝牙地址、校准数据、备份、密码，以及包含这些信息的日志，只放 `private/`，私有仓也不提交。密码只通过环境变量传递。
- 修复必须进入可导出的补丁序列（内核仓的提交），不能只存在某个临时工作目录。

## 5. 提交与署名

- 第一天和用户定好：提交作者、仓库账号、仓库名、许可证。发布后再改要重写历史。
- AI 完成的提交只加 `Co-Authored-By:`，不伪造人类署名，不代人加 `Signed-off-by` 或 `Tested-by`。
- 引入第三方提交保留原作者、日期和签名，记录来源仓库和提交。
- 推送、建仓、发版、改可见性、重写历史，每一项都先问用户。

## 6. 做事的规矩

- 一次只改一个变量，实验前想清楚怎么判断结果。
- 同样的失败第二次出现就停下来找最早出错的层，不写第三个补丁。
- 不用全局开关、屏蔽模块、固定延时、无条件重试掩盖问题；确实需要临时绕过时登记技术债。
- 设备同一时刻只有一个操作者（人或 agent），每条设备命令带 serial。
- 能自动测的不交给用户；能用只读手段测量的不用提问代替。
- 用户只做必须由人完成的事，提前通知时间，一次做完。

## 7. 工作量估算

不要按人日估。按下面的方法估一个区间：

1. 对每个子系统，列出还不确定的层：供电时钟、总线协议、内核驱动、远端处理器固件和协议、用户态、输出。已经在同 SoC 真机验证过的层不算；别人"声称支持"不算验证。
2. 每个不确定的层按 2 到 5 轮真机测试估。闭源协议、远端处理器、显示链路按上限；有厂商源码可读按下限。
3. 每轮真机测试约 10 到 30 分钟（构建、启动、观察、恢复、等电量）。需要用户在场的按用户可用时间算。
4. 加上几乎必然出现的成本：主机端脚本的问题、设备不在手边的时间、重复踩已知的坑（先读 `experience/` 可以大部分避免）。
5. 输出：时间区间、最大的三个不确定因素、什么条件下区间会缩小。

真正的瓶颈通常是可用的真机测试次数，不是代码量。显示、音频、Wi-Fi 往往最耗时。效率最高的情况是"设备在线、候选已准备好、授权明确"，要为这种时段做准备，而不是在设备不在时堆积未测试的候选。

## 8. 子 agent 分工

- 主 agent 负责计划、验收和与用户沟通，亲自核对关键证据（哈希、差异、真机结果）。
- 子 agent 做范围明确的具体工作：打补丁、构建、跑测试、整理资料。它的输出只是候选结果，它说"已测试"时要看测试方式是否与真实使用方式一致（冷启动还是运行中切换、真机还是模拟器）。
- 任务说明写清：目标、唯一的做法、允许改的文件、一条验证命令和通过标准、停止条件（完成、同一错误出现两次、超时、需要设备或需要决策）、要更新哪些记录。
- 不给开放式任务。开始后不久检查一次方向，方向错了立刻停掉。
- 子 agent 默认不碰设备；两个子 agent 不共享源码目录、输出目录或设备。
- 上机前让一个独立的子 agent 专门挑错，常能在上机前发现严重问题。
