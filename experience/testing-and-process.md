# 测试判断、自动化、协作与流程

## 坑

### 把"跑起来了"当成"能用了"
标记：【高频】
- 现象：显示"通过"只是影子缓冲有图；蓝牙"通过"只是 `hci0 up`，从没扫描过；服务 active、probe 成功、QEMU 通过都被写成功能通过。
- 怎么解决：功能通过必须是用户能感知的结果（看到、听到、摸到、连上）或等价的硬件指标，并与人眼确认分开记录。
- 适用范围：通用。

### 离线检查全绿，被当成"接近交付"
标记：【高频】【耗时】
- 现象：几十个离线检查、重复构建比对、QEMU 全部通过，候选被叫"最终版"；上机后本版新增的功能全部失败。
- 原因：时间花在容易产生通过记录的检查上，而不是最能否定方案的真机证据上；模拟数据用了虚构的地址和换行符；模拟数据和被测代码基于同一个错误假设。
- 怎么解决：只有离线证据的写"离线通过"；每个新功能先用独立的内存镜像单项上真机，通过后再合并；测试数据至少保存一份真机原文。
- 适用范围：通用。

### 运行中切换测试代替冷启动测试
标记：【高频】【致命】
- 现象：开关调试通道、改 socket 在运行中测试都正常，正式版冷启动卡 90 秒或通道完全不起来。
- 怎么解决：改 unit、socket、udev、initramfs、生成器、启动参数后，用"改动已经生效的镜像"冷启动验证，并先用旧版本复现问题作对照；发布前列出自上次真机验证后改过启动路径的包，每个都要有冷启动记录。
- 适用范围：通用。

### 主机端脚本的问题浪费了真机机会
标记：【高频】
- 常见形式：写死主机 IP（DHCP 实际给的是别的地址）；只模拟了 LF 换行而真机是 CRLF；USB 断开不保证 TCP 收到 FIN，旧连接 90 秒没有 EOF 被当成设备还在线；shell 回显里包含结束标记导致提前截断；`fastboot boot | tee` 返回的是 tee 的退出码；读回命令丢了 stderr 得到空输入的哈希（`e3b0c442…`）；BusyBox 行编辑最多 1023 字节；提示符后跟 `\x1b[6n`；`nmcli -t` 在 pty 下带颜色码；设备重新枚举后主机 fastboot 挂住（解绑重绑 USB 端口可恢复）；Fastboot 刚交接时轮询撞上 ABL 拆 USB 窗口误发命令。
- 怎么解决：用户到场前在真机上完整跑一遍主机侧检查（USB 接口、地址、路由、Fastboot 身份、换行符、命令长度）；用明确的开始和结束标记界定每条命令的输出；空输入哈希当失败；EOF 不当成功；同类主机错误第二次出现时扫一遍所有入口。
- 适用范围：通用。

### 判断标准、测试数据或测试工具自身有缺陷
- 现象：编排器异常被记成通过；测试包装器把失败报成成功；探针杀掉了自己的负载后判失败；温区前缀表漏项；验收采集在开机后太早（例如 45 秒内）把"仍在启动"误报为失败。
- 怎么解决：最早出错的层可能是工具本身；编排器异常一律判失败并保存堆栈；每个检查准备一个应该失败的输入；修好工具后对已保存的证据离线重新判断，不重跑设备、不放宽标准。
- 适用范围：通用。

### 用户测试窗口太短，或没提前通知
- 现象：30 秒的按键窗口过去了用户才知道；结果记成"失败"。
- 怎么解决：需要用户动作时提前至少一分钟通知，说明要做什么和观察什么；能用长时间记录器（例如运行数小时的 evdev 记录）代替窗口的就用记录器；用户报告的物理结果直接记录，与机器证据分开。
- 适用范围：通用。

### 让用户做本可以自动完成的事
- 现象：反复请用户截图、打开应用、点按。
- 怎么解决：经调试通道自动化桌面测试：截图用桌面门户（xdg-desktop-portal）的 Screenshot 接口并预先授权，避免弹窗；输入注入用 Mutter 的 RemoteDesktop 虚拟输入，不必走 uinput；锁屏时截图是全黑的，测试前先解锁（测试机可以关掉自动锁屏，不进产品）；新版 GNOME 没有列窗口的接口时用截图判断。注入的事件只证明软件链路，真实手指至少确认一次。
- 适用范围：GNOME；2026。

### 两个任务同时操作同一台设备
- 现象：别的任务重启设备，污染了实验；一次"USB 重连成功"其实来自另一个任务的重启。
- 怎么解决：同一时刻只有一个操作者；任何设备命令前检查是否有其他进程在用设备；每份证据绑定启动 ID；没有启动 ID 的主机日志不能用于归因。
- 适用范围：通用。

### 同样的失败第二次出现，还在修末端症状
标记：【高频】【耗时】
- 现象：同一类失败反复出现，每次都在末端补一个修复（例如在协议层修一个其实是供电问题的超时）；这是最常见的大块时间损失。
- 怎么解决：停下来，从物理层往上逐层找最早出错的地方：供电和时钟、总线电平、协议、驱动、用户态所有权、输出、观测手段本身；写下已排除的假设和下一个能证伪的实验。
- 适用范围：通用。

### 在已经挂死的启动里做"排除"实验
- 现象：多轮对照全部"无效"，错误结论被写进了代码注释或文档。
- 怎么解决：每次排除实验从干净的新启动开始，并记录开机时长。
- 适用范围：通用。

### 判定"这个改动没用"太早
- 原因：同时存在另一个错误，正确的修复也表现为无效。
- 怎么解决：判定无效前说明其他条件为什么都对；说不清时写"在当前未知条件下没有看到改善"。
- 适用范围：通用。

### 结论在上下文压缩或换人后丢失，同一个错误被重新引入
- 怎么解决：否定过的方案和撤销过的改动写进 NO-GO 记录；上机前对照。
- 适用范围：通用。

### 子 agent 绕圈子、过度设计，或把未验证的改动留在树上
- 现象：开放式任务跑两小时产出无法验证的代码；按"缓存发行版层"的任务写了几百行缓存代码，但瓶颈根本不在那。
- 怎么解决：任务说明只给一种做法、允许改的文件、一条验证命令和通过标准、停止条件；开始后不久检查方向，偏了立刻停；子 agent 的"已测试"按未验证处理，除非测试方式与真实使用方式一致。
- 适用范围：通用。

### 用提问代替测量
- 现象：等用户回答一个问题等了几个小时，而这个问题本来可以用只读的远程诊断手段直接测出来。
- 怎么解决：能自己测的先测。
- 适用范围：通用。

### 没先看同类项目就设计
- 现象：自己设计的流程（例如安装方式）踩了同类项目早已解决的问题；同类项目复盘里记录过的坑又踩一遍。
- 怎么解决：设计任何流程前，先读同 SoC 和同作者项目的安装器、复盘和技术债。
- 适用范围：通用。

### 复用社区成果时先比较"地基"
- 现象：想直接换成社区的内核，发现社区的量产镜像依赖原厂设备树加 overlay、全局资源保活参数和自写 init，独立设备树只是骨架。
- 怎么解决：先比较设备树路线、资源管理方式、init 和安装方式；地基不同时按功能系列整组导入（显示、充电、相机），板级数值仍取本机；地基相同时直接换基线。
- 适用范围：通用。

### 文档对外泄露内部信息或说法不一致
- 现象：README 里出现内部代号和实验编号；发布说明全是哈希；三处文档对同一功能说法不同。
- 怎么解决：对外文档只写给第一次接触项目的人；一个结论只写在一个地方；发布前由主 agent 亲自审一遍。
- 适用范围：通用。

### 用一个数据点编出根因
标记：【高频】
- 常见形式：一次失败就归因于某个显眼的属性（例如镜像大小），换一个变量再测就被推翻；用休眠中不走的时钟算睡眠时长，得出"自醒"；在暗场景或特殊负载下判断显示缺陷，对照组其实一样。错误结论一旦交给子 agent 去"修"，浪费会成倍增加。
- 怎么解决：报告根因之前，用第二个数据点或一个对照组试着推翻它；测量方式本身要先确认可信（时钟源、光照、场景）。
- 适用范围：通用。

### 无人值守时卸载或重绑真实硬件驱动，设备变得不可达
标记：【致命】
- 现象：卸载驱动卡住，随后正常重启卡在关机阶段，调试通道早已断开，只能等用户按键。
- 怎么解决：无人值守时不卸载、不重绑真实硬件驱动；要换模块就在重启前暂存，用新的 RAM 启动验证；重启前检查 D 状态任务，有就用 SysRq 重启。
- 适用范围：通用。

### 候选内核直接写进启动槽，GPU 挂死后普通重启卡在关机
标记：【致命】
- 现象：在已安装的系统上用包管理器升级候选内核，包钩子写了活动槽；跑应用覆盖测试时 GPU 报 `timeout waiting for GMU OOB set GPU_SET`，之后每次 hang 恢复都失败。随后发出普通 `reboot`，关机卡在 DRM 收尾，USB 调试通道已断，又没有可用的硬件看门狗，设备几个小时不可达，只能等人长按电源键。回退槽在此前重装同一版本的重建包时，也被换成了同一个候选。
- 原因：本经验库里已有的三条规则（候选先 RAM 启动并带挂死即 panic 的参数；重启前查 D 状态任务、用 SysRq；保留已知可用的回退）只写在经验库里，没有写进执行者拿到的任务说明。执行者遇到第一个硬件故障后继续操作，没有停下。
- 怎么确认：主机上设备的 USB 网卡还在但没有流量，adb 和 Fastboot 都找不到设备；强制重启后，上一次启动的日志停在 GPU 恢复和关机阶段。
- 怎么解决：长按电源键强制重启。之后先用 RAM 启动验证候选，命令行带 `softlockup_panic=1 hung_task_panic=1 panic_on_oops=1 panic=10` 并设限时重启，再恢复已知可用的回退槽。
- 怎么预防：
  - 把这几条做成每一份涉及设备的任务说明的必写约束，不能只放在经验库里。
  - GPU 或驱动已经挂死、或者存在 D 状态任务时，只用限时 `sync` 加 SysRq（s、u、b），或者 `systemctl reboot -ff`。
  - 第一个硬件故障出现就停测、取证、强制重启并汇报，同一次启动里不再继续测试。
  - 调试版在运行时也武装 hung-task panic 和 panic 后自动重启。
  - 重装同一内核版本的重建包时，不让它轮换掉回退槽。
- 适用范围：通用。

### 底层通过了就关闭用户层面的问题
- 现象：相机测试脚本能取帧就关闭了"相机不可用"，用户打开应用仍然没有相机。
- 怎么解决：关闭用户报告的问题，验收要走用户实际使用的入口。
- 适用范围：通用。

### 测试被桌面的自动行为干扰
- 现象：背光寄存器检查失败，其实是 GNOME 自动亮度改写了值；GUI 测试在没有会话环境的 shell 里启动应用失败。
- 怎么解决：测试前关掉会干扰的自动行为（测试结束恢复）；GUI 测试从会话里取环境（`systemctl --user show-environment`）或用桌面自动化工具启动。
- 适用范围：GNOME；2026。

### 审查社区贡献
- 做法：能合尽合，小问题自己补提交；与项目范围无关或有法律、道德风险的内容（例如伪造原厂更新器身份绕过下载限制）不收；合入后记录作者和来源。
- 适用范围：通用。
