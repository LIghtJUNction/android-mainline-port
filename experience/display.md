# 显示

## 推荐路线

屏幕点亮有两种方式，先理解差别再选：

| | 借用固件画面（simple-framebuffer + simpledrm） | 原生接管（DPU + DSI + 面板驱动） |
|---|---|---|
| 原理 | bootloader 已点亮面板并让显示控制器循环扫描一块内存，Linux 只往这块内存画图 | 内核的显示驱动重新初始化控制器和接口，面板驱动重新发上电命令 |
| 首次出图 | 快（一两天） | 有现成面板驱动时几天；自写面板驱动可能一到两周 |
| 能力 | 没有亮度调节、真正熄屏、刷新率切换、外接显示、休眠前提；GNOME 看到的连接器类型是 Unknown | 全部具备 |
| 主要风险 | 资源回收（见 `kernel-and-resources.md`） | 参数错误导致花屏、熄屏亮屏生命周期 |

**建议**：上游显示驱动支持这个 SoC、面板驱动可以从社区或厂商代码拿到时，直接原生接管。否则先借用画面打通安装链路和桌面，**同时**开始原生接管；不要在借用画面上做亮度、熄屏之类的产品修补。

### 原生接管的步骤

1. 在原厂系统用原厂驱动的 debugfs 保存"黄金快照"：时钟树、管线拓扑（mixer、DSC、接口数量）、DSC 参数、PHY 时序、面板上电命令。不要用 `/dev/mem` 扫描显示寄存器。
2. 面板驱动：优先复用社区或上游现成的；上电命令从厂商 dtsi 机械提取，与本机原厂设备树逐条核对。
3. 先用模块方式加载显示驱动（`msm` 做成 `=m`，启动时不加载，调试通道起来后手动 `modprobe`），这样挂死前能拿到日志。
4. 把显示子系统加入 SMMU 的直通（identity）列表，让固件画面能撑到驱动复位那一刻（上游对部分 SoC 已有先例）。
5. 先在固件当前的刷新率下完成接管，再做其他刷新率。
6. 验收后再做熄屏、亮屏、背光关联、DPMS。

## 完成标准

- 人眼看到正确画面（首次必须）。
- 硬件指标：显示接口帧计数按刷新率增长；没有欠载（underrun）和 DSI 错误；原生接管时 debugfs 里的拓扑与黄金快照一致、CRTC CRC 稳定、面板状态寄存器读回正常（例如 DCS `0x0A`）；借用画面时显存区域采样有多种颜色、显示总线互连每一跳都有投票。
- 多次冷启动都满足时间预算；熄屏再亮屏多轮后画面和触控都恢复。
- 不算通过：进程在运行、`/dev/fb0` 能写、显存里有图、connector 状态 connected。

## 坑

### 把借用固件画面当成产品路线
标记：【高频】【耗时】
- 现象：桌面能用，但没有亮度条，熄屏只是黑画面背光常亮，设置里刷新率显示 60 Hz，挂起和外接显示没有前提；为维持它又花数天处理资源回收。
- 原因：simpledrm 只拥有一块内存，不管硬件；GNOME 对 Unknown 连接器不提供内屏功能。
- 怎么解决：借用画面只用于首次点亮和打通安装链路，原生接管尽早并行开始。
- 适用范围：通用；2026。

### 软件状态全部正常，屏幕却是黑的，被误判为"已点亮"
标记：【高频】【耗时】
- 现象：connector、fb0、fbcon、背光寄存器全部正常，用户看到纯黑；甚至得出"面板坏了"的错误结论。
- 原因（常见叠加）：背光芯片的总使能寄存器从未写（主线把它当只读 ID）；DSC 视频模式面板用了非连续时钟导致失锁；TE 引脚没接导致 vblank 超时；DSC 参数与面板解码器不一致；接口有效宽度取整不一致；面板供电电压不在 PMIC 步进上导致整颗 PMIC 消失。
- 怎么确认：全黑先查背光（背光不依赖面板）；把厂商显示驱动源码逐项对完再做黑盒二分。
- 怎么解决：按厂商实现修正每一项。
- 提前预防："点亮"只由人眼或面板侧硬件指标判断。
- 适用范围：通用；2026。

### DSC 参数不一致：条纹、花屏、彩条却能通过
标记：【高频】【耗时】
- 现象：画面有横向条纹或块状错误；纯色彩条看起来正常。
- 原因：DSC 码率控制（RC）参数表版本（1.1 与 1.2）、`first_line_bpg_offset`、`initial_lines`、slice 宽度取整、`slice_per_pkt` 与面板解码器不一致；主线驱动可能用自己的默认 RC 值覆盖面板驱动提供的值。
- 怎么确认：用跨 slice 的压力图测试（彩条在 RC 错误时也能通过）；把派生值与面板的 PPS 数据逐字段对比。
- 怎么解决：按面板（厂商）实际值设置，确认驱动没有覆盖。
- 适用范围：高通 DPU + DSC 面板；2026。

### 管线拓扑选错：零报错但全屏花屏
标记：【耗时】
- 现象：所有组件 active、PPS 已发、无错误，画面是花的；多轮"单变量调参"都无效。
- 原因：拓扑选了 4 个 mixer，而非虚拟平面只能喂 2 个，另一半是垃圾数据，压缩器把垃圾正常编码。
- 怎么确认：先看 `/sys/kernel/debug/dri/0/state` 里的 `mixer=`、`dsc=`、`stage=`，与厂商拓扑对比。
- 怎么解决：没有虚拟平面时不选四路拓扑。
- 提前预防：拓扑错的时候，其他正确的修复（例如 `slice_per_pkt`）也会表现为"无效"。判定某改动无效前先确认其他维度正确。
- 适用范围：高通 DPU；2026。

### 模式校验拒绝高刷新率，或可用模式数为 0
- 现象：`MODE_CLOCK_HIGH`；连接器 0 个模式；某个刷新率（例如 144 Hz）不可选，而社区版本可以。
- 原因：模式校验用 bootloader 残留的时钟作为上限；或按分辨率算出的显示核心时钟略高于 SoC 上限（例如需要 577 MHz，上限 575 MHz）。社区可能直接改掉了这条检查。
- 怎么解决：上限用驱动可达的最高频率而非残留值；高刷新率先在固件默认刷新率下完成接管，再评估考虑 DSC 压缩后真实带宽的修正。不要为了通过校验把时钟抬到 OPP 表之外（会导致 `-ERANGE` 和投票丢失）。
- 适用范围：高通 DPU；2026。

### 只启用显示子系统节点、没有任何组件时，显示驱动空指针
- 现象：启用 MDSS/DPU 节点后启动早期挂死，没有 USB。
- 原因：DPU 没有任何组件时把空列表交给 component 框架，空指针。
- 怎么解决：无组件时返回 `-ENODEV`（上游级一行修复）；显示驱动先做成模块手动加载就能拿到 oops。
- 适用范围：主线 msm 驱动；2026。

### 启用显示子系统节点后，固件画面立刻损坏
- 现象：驱动还没复位硬件，画面就已经花了。
- 原因：SMMU 在启动早期把显示流接到新的地址域，固件扫描的内存开始缺页。
- 怎么解决：把该 SoC 的显示子系统 compatible 加进 SMMU 的 identity 域列表。
- 适用范围：高通；2026。

### 熄屏后再亮屏失败
标记：【高频】【耗时】
- 现象：亮屏后 DSI 命令 DMA `-110`、`CTL_FLUSH` 卡住、频繁 vblank timeout 花屏，或 `dsi_err_worker status=4`；静止登录界面测试却"通过"。
- 原因（已确认的一例）：显示电源域掉电前缺少 VBIF AXI halt 握手；CTL 软复位永不完成，需要 override；恢复时先开时钟后投票。
- 怎么确认：逐项对照原厂驱动的 power-event 钩子；每次对照实验从干净的新启动开始，在已经挂死的启动里做"排除"实验没有意义。
- 怎么解决：按原厂顺序补握手和复位；恢复时先投票再开时钟。
- 提前预防：显示验收必须注入新帧（移动鼠标或打开窗口），commit 和 vblank timeout 一律判失败。
- 适用范围：高通 DPU；2026。

### 接管时屏幕会黑一下
- 现象：原生驱动加载时画面消失约 1 秒。
- 原因：上游没有无缝接管，驱动通过 aperture 移除 simpledrm 后复位硬件。
- 怎么解决：属于正常现象，文档里说明即可。
- 适用范围：主线；2026。

### GNOME 测试清理代码把登录区移出屏幕
- 现象：软件全绿但用户看到全黑或没有登录框。
- 原因：测试脚本调用 `org.gnome.ScreenSaver.SetActive(false)`，gnome-shell 隐藏锁屏时把登录区平移出屏幕。
- 怎么解决：不要调用 `SetActive(false)`；唤醒只发一次无文本按键；调用 GNOME D-Bus 接口前读 gnome-shell 源码确认语义。
- 适用范围：GNOME；2026。

### 系统恢复上次关机时的亮度，开机很暗
- 原因：systemd-backlight 保存并恢复了一个很低的亮度。
- 怎么解决：在显示管理器之前用一次性服务写默认亮度，不要用 dconf 锁。
- 适用范围：systemd 系统。

### 多颗背光芯片
- 做法：每颗芯片作为 LED 子设备，用 `led-backlight` 聚合为一个背光设备，并在面板节点里关联，桌面才会给亮度条。
- 适用范围：通用。

### 熄屏时花屏或大量欠载
标记：【耗时】
- 现象：DPMS 关屏瞬间画面花掉，欠载计数大量增加；重新亮屏后可能正常。
- 原因：双 INTF 的配置里，在停止接口之前就清理了 CTL；关闭顺序与原厂不同；从 DSI PHY 的状态没有保存和恢复。
- 怎么解决：按原厂和社区修正的顺序先停 INTF 再清 CTL；导入 DPU 关闭顺序和从 PHY 保存恢复的补丁。验收做几十次 DPMS 循环，数欠载事件。
- 适用范围：高通 DPU 双 DSI；2026。

### frame-done 或 pending 超时告警，但画面完全正常
- 原因：上游 `dpu_crtc_commit_kickoff()` 在 encoder kickoff 之后才置位定时器，重启后的第一个 vsync 可能先清掉状态，产生无害的记账告警。
- 怎么解决：不要把它当作显示故障；需要时按上游顺序修正并保留真实超时的检出能力。
- 适用范围：主线 msm；2026。

### 夜灯（色温调节）
- 做法：高通需要 DSPP 的 GC/GCv2 和 REGDMA 支持，社区已有实现，按来源导入；GNOME 50 的夜灯不经过 Mutter 空 LUT 的缺陷路径，不必改发行版 Mutter。
- 风险：REGDMA 复位得不到确认时，原实现会无限等待；要给退出加时间上限，并在超时时保留仍被 DMA 使用的映射，不能释放。
- 适用范围：高通 DPU；2026。

### 高刷新率最终可以工作
- 补充：社区修正模式校验后，双 INTF 144 Hz 在本机稳定运行；60/90/120/144 四档切换和 CRC 验证通过。高刷新率要连同触控一起测（见 `touch-and-input.md`）。
- 适用范围：高通 DPU + DSC 面板；2026。

## 未解决

- 熄屏后再亮屏和休眠唤醒时 `dsi_err_worker status=4`：同 SoC 的社区实现也没有解决。
- 部分 DSC 面板的高刷新率需要更准确的显示核心时钟算法。
