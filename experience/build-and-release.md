# 构建流水线与发布

环境搭建的完整做法见 `../references/build-environment.md`。这里只记具体的坑。

## 坑

### 构建很慢，但从没分段计时
标记：【高频】【耗时】
- 现象：根镜像每次构建 40 分钟以上，换了几种"提速"方法都没用。
- 原因：没有测量就猜瓶颈。实测分段后发现大头是 QEMU 全系统模拟里的 dracut（约 15 分钟）和 purge 通用内核，而不是发行版包。
- 怎么解决：每一步记录耗时；第一次出现超过 5 分钟的步骤就分段计时；按测量结果决定优化什么。
- 适用范围：通用。

### 换了 OUT 目录，ccache 全部失效
- 现象：一次本该一分钟的增量构建变成 40 分钟冷构建。
- 原因：为了"干净"新开 OUT 路径，路径进入了编译参数和缓存键。
- 怎么解决：每种配置一个长期 OUT；ccache 设 `base_dir`；只有正式发布前做一次干净构建。
- 适用范围：内核构建；通用。

### ccache 容量太小
- 现象：`ccache -s` 显示缓存已满、清理上千次、命中率不到一半。
- 原因：上限只有 4 GB，又没设 `base_dir`，每次在新路径下构建都给 manifest 追加条目（实测 manifest 占了缓存的六成多）。
- 怎么解决：上限 10 GB（只做内核时足够，约 30 次完整构建）；设 `base_dir` 并固定 OUT 路径；定期看命中率。`ccache --show-compression` 和按文件后缀统计（`M` 是 manifest，`R` 是结果）可以看清空间花在哪。
- 适用范围：通用。

### 在 x86 主机上用 QEMU 全系统模拟构建 ARM64 根文件系统
- 现象：装包阶段 30 分钟以上；同时跑两个虚拟机时计时翻倍。
- 怎么解决：优先原生 ARM64（例如 GitHub Actions 的 arm64 runner，同样的构建十几分钟）；其次 root 权限下的 qemu-user chroot（约快一倍）；全系统模拟只用于必须验证 init 行为的测试；不要并行跑多个全系统虚拟机。
- 适用范围：通用；2026。

### 无 root 的用户命名空间 chroot 做不出正确的根文件系统
- 现象：`/etc/shadow` 属主从 `0:42` 变成 `0:0`；`mknod` 失败，initramfs 少设备节点。
- 原因：`unshare -r` 只映射一个 UID/GID；没装 `newuidmap` 时不能多映射；命名空间里也不能 `mknod`。
- 怎么解决：用真正的 root（给构建机一条只允许固定脚本的免密 sudo），或用原生 CI。
- 适用范围：通用。

### 降低 dracut 压缩等级没有效果
- 原因：Ubuntu 的 dracut 用 3cpio 打包，`zstd -1` 和 `-19` 都被映射到同一个等级。
- 怎么解决：不要在这上面花时间；日常迭代改为在设备上装包、在设备上生成 initramfs（几十秒）。
- 适用范围：Ubuntu 26.04；2026。

### 在 qemu-user 下编译 Mesa 极慢
- 原因：NIR 的 Python 代码生成器在 qemu-user 下运行一百多分钟，原生只要几十秒。
- 怎么解决：交叉编译或原生 ARM64 编译。
- 适用范围：Mesa；2026。

### 缓存了错误的层
- 现象：花几百行代码缓存发行版基础层，构建反而更慢。
- 原因：没先测量，瓶颈不在那一层。
- 怎么解决：先测量再缓存；只缓存确实慢且输入不变的产物，按输入哈希做键。
- 适用范围：通用。

### 对 60 GiB 原始镜像算哈希
- 怎么解决：只对最终发布的文件（例如 sparse 镜像或 tar）算哈希。
- 适用范围：通用。

### 输出目录被另一个任务改写，或编译了错误的源码版本
- 现象：已记录身份的构建产物中途被替换；构建的其实是另一个分支的提交。
- 怎么解决：同一 OUT 同一时间只有一个写入者（`flock`）；已记录身份的 OUT 不再写入；构建前自动核对源码 HEAD；记录构建输入身份，不匹配就拒绝。
- 适用范围：通用。

### 同样的源码构建出不同的结果
- 原因：ccache 与直接 GCC 的调试信息源文件名不同；漏了 `KAFLAGS` 的路径映射，汇编调试信息带进了本机路径；umask 改变目录权限；apt 索引没固定；宿主 `dtc` 版本不同；AVB salt 默认随机。
- 怎么解决：`KCFLAGS`/`KAFLAGS` 都加 `-ffile-prefix-map`；固定 `KBUILD_BUILD_TIMESTAMP/USER/HOST`；归一化权限和时间戳；`tar --sort=name`；AVB salt 固定。
- 适用范围：通用。

### 版本标签让打包脚本找错版本
- 原因：打包脚本用 `git describe` 找内核版本标签，被项目发布标签截住。
- 怎么解决：`git describe --match 'v[0-9]*.[0-9]*'` 之类限定匹配。
- 适用范围：通用。

### 清理磁盘时删掉了发布流程还要用的文件
- 现象：发布中途发现 GPL 源码包、某个 deb 不见了，只能重新下载或重打包（哈希变化）。
- 怎么解决：清理前先核对哪些路径被发布清单和收据引用；带提交的 worktree 不能当缓存删；身份记录先移到待删目录外。
- 适用范围：通用。

### 构建检查可以被环境变量绕过
- 怎么解决：检查不留后门；分支从产品 HEAD 长出，否则会把退役的参数带回来。
- 适用范围：通用。

### 发布的坑
- GitHub Release 单个附件上限 2 GB：根文件系统分卷（例如 1900 MB 一片），附校验和与合并说明。
- 发布说明和 README 里出现内部代号、实验编号、哈希堆砌：用户看不懂。发布说明只写能做什么、不能做什么、怎么装、怎么校验。
- 附件过多：合并为启动镜像包、工具包、软件包包、根文件系统分卷、校验和、清单几类。
- 提交作者第一天定好，发布后改写历史代价很大。
- 用 `gh repo fork` 时如果账号下已有同上游的 fork，会把那个 fork 改名。
- GPL 组件（例如 BusyBox）随发布附源码；发行版商标按"基于某发行版、非官方"的方式写。
- README 首页提供"让 AI 帮你安装"的提示词，用户复制给 AI 即可按文档操作。
- 适用范围：GitHub；2026。

### 软件包版本号比测试机上已有的内部版本还小
- 现象：发布版本 0.1.1，测试机上装的是内部计数 0.1.76，APT 把升级当成降级。
- 怎么解决：发布版本号要大于所有装过的内部版本；内部构建用 `~dev` 之类的后缀。
- 适用范围：Debian 打包；2026。

### 发布后移动了标签
- 现象：为改写提交作者，把已发布的标签改指到新提交。
- 怎么解决：已发布的标签不可移动；需要更正时发新版本。
- 适用范围：通用。

### 为空分区和根分区建满容量的 ext4 再转 sparse
- 现象：镜像准备阶段很慢、占用大量磁盘。
- 怎么解决：空分区在设备上格式化；根分区用 tar 或只编码已用块。
- 适用范围：通用。

### Mesa 构建不支持增量
- 现象：构建入口默认删除旧构建目录，`--resume` 又拒绝已经开始打包的目录。
- 怎么解决：构建目录按源码和补丁的哈希保留，支持增量重编。
- 适用范围：Mesa 自编；2026。

### 主机本身成为瓶颈
- 现象：镜像处理只有约 10 MB/s，发布上传很慢。
- 原因：主机盘（例如 QLC）超过九成满；桌面环境常驻占用大量内存；多个大构建并行；上传走 Wi-Fi 上行。
- 怎么解决：保持磁盘余量；大构建错开；上传用有线网络。
- 适用范围：通用。

### 按版本推进
- 做法：每个版本先写定范围和验收方式 → 开发 → 测试 → 收尾发布 → 清理分支、worktree 和旧产物 → 再继续移植。未发布的候选不要堆积；新功能等当前版本发布后再开。
- 适用范围：通用。

### 对外文档写了内部问题
- 现象：README 和发布说明里写了调查中的问题、技术债编号、根因分析，用户看不懂也不关心。
- 怎么解决：对外文档只写完成了什么、支持什么、怎么用；保留安全相关的提醒（清数据、备份、槽位规则）；不支持的一句带过；已知问题最多几条用户能感知的，不讲根因。
- 适用范围：通用。
