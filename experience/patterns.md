# 问题模式：遇到故障先判断属于哪一类

各领域文件里的坑，抽象下来大多属于下面几类。遇到新问题时，先对照"怎么认出来"判断类别，按"通用处理"排查，再去对应文件找具体条目。一个现象可能同时属于两类。

| 类 | 一句话 |
|---|---|
| A | bootloader 改了你以为没变的东西 |
| B | 资源没有真正的拥有者 |
| C | 时序和生命周期不对 |
| D | 残留状态让结果失真 |
| E | 测量方法本身错了 |
| F | 底层通过不等于用户能用 |
| G | 上游或发行版已经修了 |
| H | 别人的实现不能整搬 |
| I | 恢复路径本身不可靠 |

---

## A. bootloader 改了你以为没变的东西

**怎么认出来**：同样的内核和设备树，`fastboot boot` 返回 OKAY 却没反应；按 compatible 匹配的代码全部失效；命令行改了不生效；systemd 判断的机型不对；槽位行为和预期不同。

**通用处理**：
1. 取 bootloader 输出端的状态：原厂系统的 `/sys/firmware/fdt`、新系统的 `/proc/device-tree`、`/proc/cmdline`、`/proc/bootconfig`、`fastboot getvar all`、失败原因查询。
2. 和你打包的输入逐项对比，差异就是 bootloader 做的事。
3. 离线用 bootloader 实际使用的实现复现，先跑原厂正对照。
4. 修正的位置优先放在打包阶段（注入符号、校验身份），或在内核早期恢复原值；凡是会被改写的属性都不要用来判断设备。

**常见表现**：缺符号表静默拒绝、设备树身份不匹配停在 Fastboot、根 compatible 被改写、hypervisor 节点导致虚拟机误判、命令行来自设备树且有长度上限、序列号只在 bootconfig、槽状态不只是属性位。见 `bootloader-and-boot.md`、`usb-and-storage.md`。

## B. 资源没有真正的拥有者

**怎么认出来**：启动后几秒到十几秒某个功能消失；多个看似无关的子系统同时超时（显示、GPU、触控）；部分启动正常、部分启动整体变慢；外设能枚举但总线没电；加了一路电源后整颗 PMIC 消失；sync_state 一直挂起，SoC 跑在最高电压。

**通用处理**：
1. 在资源回收前后各导出一次 `clk_summary`、`pm_genpd_summary`、`interconnect_summary`、`regulator_summary`，看哪些在回收后被关掉。
2. 和原厂的常开电源、时钟、带宽投票做差集。
3. 把需求写进真正的消费者节点，提供者驱动内建并早于回收点绑定。
4. 电压值按驱动的电压表机械校验，用原厂寄存器的实际值。
5. 不用全局忽略、屏蔽模块、超时释放来掩盖。

**常见表现**：借用固件画面被回收、显示时钟控制器是模块导致慢启动态、假消费者让 sync_state 永不完成、常开电源缺失导致键盘总线低电平、电压不在 PMIC 步进上。见 `kernel-and-resources.md`、`display.md`。

## C. 时序和生命周期不对

**怎么认出来**：偶发；与刷新率、熄屏、休眠、拔插、开机时外设是否已连接有关；手动重启服务就恢复；"手动执行成功、作为服务失败"；加延时看起来能好。

**通用处理**：
1. 同时记录相关事件的时间（面板回调、显示 kickoff、首个中断、服务启动、设备出现）。
2. 对照原厂驱动的生命周期（熄屏、亮屏、休眠、唤醒各做了什么、顺序如何）。
3. 回调里不做阻塞等待；依赖的设备用事件驱动（等它出现）而不是固定延时。
4. 对比"手动"和"服务"两边的执行环境（标准输入输出、权限、命名空间、`systemctl show`）。
5. 不用周期保活、自动复位、固定延时、服务自动重启当修复。

**常见表现**：TDDI 熄屏后触控固件丢失、面板回调里同步等首帧、触控命令发得太早、键盘电源状态没按原厂写、充电控制休眠交接、PCIe 保留链路却关了电源域、socket 绑定开机时还不存在的网卡、oneshot 服务反复运行、`btmgmt` 标准输入是 `/dev/null`、Fastboot 后台写零期间不应答。见 `touch-and-input.md`、`power-and-time.md`、`wireless.md`、`ubuntu-userspace.md`。

## D. 残留状态让结果失真

**怎么认出来**：开发机上好好的，全新安装就不行；同一版本重装后行为不同；修复"突然无效"；旧数据出现在新系统里。

**通用处理**：
1. 列出所有可能残留的状态：保存的 ALSA 状态、用户配置、已装的旧包和旧内核、旧的启动镜像集、分区里的旧数据、旧的 OUT、设备上的旧本机数据副本、已移动的标签。
2. 在全新系统、新启动、空目录上复现。
3. 修复要在没有残留的条件下验收。

**常见表现**：全新安装只有 Dummy Output、sparse 跳过块残留旧数据和旧日志、换路径后 ccache 失效、传感器配置要在新启动上判断、导入过期的本机数据副本、包版本号小于测试机上的内部版本。见 `audio.md`、`usb-and-storage.md`、`build-and-release.md`、`sensors-camera-media.md`。

## E. 测量方法本身错了

**怎么认出来**：结论只来自一个数据点；判据依赖的时钟、场景、环境没核实过；离线全绿而真机失败；"修好了"之后马上又坏。

**通用处理**：
1. 先确认测量可信：用哪个时钟、什么场景（光照、负载）、什么环境（QEMU 还是真机、运行中切换还是冷启动、有没有会话环境）。
2. 报告根因之前，用第二个数据点或一个对照组试着推翻它。
3. 每个检查准备一个应该失败的输入，确认它会报失败。
4. 修好工具后对已保存的证据重新判断，不重跑设备、不放宽标准。

**常见表现**：单调时钟算睡眠时长、s2idle 只读第一段、"镜像太大"的错误解释、暗场景被当成显示缺陷、QEMU 里 Mesa 退回软件渲染、运行中切换代替冷启动、自动亮度改写背光读数、主机脚本的换行符和地址问题。见 `testing-and-process.md`、`power-and-time.md`、`gpu.md`。

## F. 底层通过不等于用户能用

**怎么认出来**：驱动加载了、节点出现了、服务 active、脚本取到数据，但用户说"不能用"。

**通用处理**：
1. 写出从硬件到用户入口的完整链路（例如相机：传感器 → 驱动 → 守护服务 → PipeWire → 应用）。
2. 逐层确认，最后一层必须是用户实际使用的入口。
3. 用户报告的问题，只有在用户入口验证通过后才关闭。

**常见表现**：取帧通过但应用里没有相机、`hci0 up` 但不能配对、影子缓冲有图但屏幕黑、扫描到热点但连不上、应用商店能开但中文全是方块。见 `testing-and-process.md`、`sensors-camera-media.md`、`wireless.md`。

## G. 上游或发行版已经修了

**怎么认出来**：问题出在发行版自带的组件或上游驱动里；上游或社区的新版本里有相关提交；你在用一个较旧的固定版本。

**通用处理**：
1. 先查上游 main、stable、发行版的新版本和 issue 列表。
2. 能直接更新就更新（例如 `snap refresh`）；否则按提交回移，登记技术债，上游发版后换回。
3. 上游没修时，写最小修正并准备提交上游。

**常见表现**：应用商店中文方块（snap 新版已修）、Turnip NV12 行距（上游 stable 已修）、频段计算和恢复期扫描（社区 FROMLIST）、设备模型引用泄漏。见 `ubuntu-userspace.md`、`gpu.md`、`wireless.md`。

## H. 别人的实现不能整搬

**怎么认出来**：照着参考设备或社区做了，本机行为不同；社区"已支持"但本机不工作。

**通用处理**：
1. 分清能搬的（驱动代码、协议、用户态）和不能搬的（电压、GPIO、时序、board 数据、校准、分区号、保活策略）。
2. 先比较地基（设备树路线、资源管理、init、安装方式），再决定换基线还是按功能导入。
3. 不能搬的部分全部回到本机原厂取证。

**常见表现**：参考 dtsi 的极性和收发脚写反、别的设备的 board 数据、另一种键盘协议的保活策略、社区靠全局保活参数跑通的功能。见 `kernel-and-resources.md`、`touch-and-input.md`、`wireless.md`、`testing-and-process.md`。

## I. 恢复路径本身不可靠

**怎么认出来**：计时到了没回去；正常重启卡在关机；设备不可达只能等人按键。

**通用处理**：
1. 恢复路径的每一步都有时限（`sync` 限时、`reboot -f -n`），并在最终组合上实测过。
2. 无人值守时不卸载、不重绑真实硬件驱动；重启前查 D 状态任务，有就用 SysRq。
3. 看门狗做受控失喂测试，确认真的会复位。
4. 产品镜像永远保留一条可打开的调试通道。

**常见表现**：到期路径里无界 `sync`、视频驱动卸载死锁后关机卡住、正式镜像没有通道、systemd 去打开 hypervisor 看门狗。见 `bootloader-and-boot.md`、`sensors-camera-media.md`、`testing-and-process.md`。
